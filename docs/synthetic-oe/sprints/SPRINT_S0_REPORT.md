## What is now known to be wrong

Nine assumptions this sprint falsified. Six of them were ours.

1. **`method.impl` does not select the implementation.** `retrieve.ipynb` derives the
   retriever from the config's *filename*, `METHOD_NAME.split("__", 1)[0]`, through an alias
   table written inside the notebook. Six configs do not set `impl` at all. A run was
   reproducible from `(config, code commit)` only because the filename happened to survive —
   renaming a config silently changes which code runs.
2. **D-016 said two configs lacked a `retriever` block. It is 72 of 77.** The original
   inventory was grep-based and sampled; parsing all of them gives the real figure. The
   decision stands; its scope was misreported.
3. **Migrating the configs does not parameterise the collection.** Seven notebooks name OEB
   files literally, outside any config. Setting `collection: "OE"` resolves correctly inside
   a config and is then ignored by the code that reads it. The config migration was the
   small half of that job (D-008, D-022).
4. **Decile stratification is not possible on 83 concepts.** It yields 30 non-empty cells of
   which 10 hold a single concept, and a singleton cell cannot be split — a tenth of the
   corpus would have been assigned arbitrarily under a stratification that looked principled.
5. **Balancing concept counts is not balancing the corpus.** Family sizes span 3 to 6 336,
   so an even split of concepts is a 62/38 split of leaves.
6. **Dev and test are not exchangeable populations for a per-type comparison.** Modification
   applicability correlates with concept, so any concept-level split skews the type mix:
   `unit_conversion` 204/345, `expansion` 130/76. The planned paired-delta analysis is
   unaffected; a per-type comparison across sides would not be valid (D-021).
7. **D-019's own Context was wrong when written.** It claimed `eval/` and `analysis/`
   survived the 2026-09-14 deletion because their files were committed and `git clean` spares
   tracked files. No `git clean` ran, and `analysis/` had no tracked files at all. They
   survived because they were not among the five junctioned paths. Corrected in place, with
   the correction recorded.
8. **The Zenodo "reproducibility release" contains no runs.** Verified by downloading it:
   zero entries under `runs/`, `index/` or `data/`. The GitHub–Zenodo integration archives
   the git tree, and those paths are git-ignored. The deposit cannot restore what the
   incident destroyed, and was never able to.
9. **`docs/reviews/` was not in the history**, although the root `CLAUDE.md` names
   `paper_28.tex` authoritative over the README results table. Committed at `912807a`. While
   doing so: the manuscript references `references.bib` and
   `elsarticle/graphical_abstract.png`, and the directory holds `references (11).bib` and
   `graphical_abstract (1).png` — download-mangled names. **The paper does not compile from
   this directory as it stands.** Left untouched; renaming is the author's call.
   *(Overtaken 2026-09-15, after this report closed, by `a391ee9`: both files were renamed to
   the names `paper_28.tex` expects. `graphical_abstract (1).pdf` is still mangled. Noted
   after audit F5 — the finding was true at `912807a` and is read here as a record, not as
   the state of the tree.)*

**Caveat on criterion 5.** It is met, and as worded it is weaker than it reads. The
*config* resolves to the OE files; the *harness* does not read that resolution (finding 3),
and the three OE feature files it resolves to are not built until S1. Anyone treating
criterion 5 as "OE can now be run" would be wrong. S1 closes the gap.

*Amended 2026-09-15 after audit F1.* At close, this criterion was evidenced by
`migrate_configs.py --target OE`. That was the wrong proof: `--target` overrides
`collection:` by design — `resolve(cfg, collection=args.target)` never reads the field — so
it proved the input *templates* expand under a supplied collection, not that any config
names OE. Every one of the 76 configs still said `OEB`. Closed by adding the 77th config,
`bm25_unigram_params__k1-0.60__b-0.35__OE.yaml` (the manuscript's best lexical variant,
k1=0.60 / b=0.35), and by `src/utils/resolve_config.py`, which resolves one config from that
config alone:

```
bm25_unigram_params__k1-0.60__b-0.35__OE.yaml
  collection:     'OE'  (from the config, nothing overriding it)
  features_meta    /work/data/processed/OE_features_meta.json   [not built yet]
  long_feats       /work/data/processed/OE_long_feats.parquet   [not built yet]
  short_feats      /work/data/processed/OE_short_feats.parquet   [not built yet]
```

Its OEB twin is untouched and still resolves to the OEB files. With 77 configs,
`migrate_configs.py` reports 0 defects and resolved inputs byte-identical before and after;
0 configs lack a `retriever` block; the new filename still yields `bm25_unigram_params`
under the notebook's `split("__", 1)[0]`, so finding 1's filename coupling is respected

**Artefacts.** `MANIFEST.md`, `SPLITS.md` (seed `20260915`), the E3 request in flight, 77

`bm25_unigram_params__k1-0.60__b-0.35__OE.yaml`, on `collection: "OE"` — and five committed

**Debt, all of it created before S0 except the last two.**

- Seven notebooks hard-code OEB filenames; three are on the critical path. D-022 is S1's
  entry decision and says how.
- The alias table inside `retrieve.ipynb` still overrides the declared `retriever.module`.
  Declaring is not obeying.
- `index/` and `hf-cache/` are empty. Any run in S1 or later rebuilds the index first, and
  the first neural run re-downloads its models.
- **There is no end-to-end regression baseline.** `runs/` was destroyed on 2026-09-14, so
  the migrations of S1 can be verified by path equality but not by comparing numbers. This
  is the cost of the incident that had not been counted until now (D-022).
- OE features do not exist: `OE_short_feats`, `OE_long_feats` and `OE_features_meta` must be
  produced before any lexical method can run on OE.
- `src/utils/config.py` is dead legacy pointing at a different dataset; only
  `index_classes.py` imports it.

**Open question S1 must answer, not inherit silently.** Whether the OEB corpus should keep
its `OEB#` template row. Normalisation drops it, so the parquets hold 47 513 rows against
the JSON's 47 514; the OE corpus carries no such row. Harmless today, confusing later.
